# test.js — MyChat 服务端并发压测

按协议完整实现的压测客户端：TCP 连接 → CH/SH 握手（RSA-PSS 验签 + X25519 + HKDF）
→ CF/SF 双向确认 → 挑战-应答登录（PBKDF2）→ 加密帧 + 心跳。

只有走完这一整套流程的连接，才算一个"有效在线用户"，所以测出来的数字是真实在线容量，
而不是"能建立多少条 TCP 连接"。

---

## 一、前置条件

| 项目 | 要求 |
|---|---|
| Node.js | **≥ 22.5**（用到内置 `node:sqlite` 造账号，无需 npm install） |
| 服务端 | `Server.exe` 已启动并在监听 |
| 端口 | 默认 **60101**（消息端口），文件传输是 60102 |

检查 Node 版本：

```bash
node -v
```

低于 22.5 会在造账号时报 `Cannot find module 'node:sqlite'`。

## 二、最快的一次完整测试

四条命令，从零到出结果。

### 1. 启动服务端

直接双击 `Server.exe`。界面里能看到"已监听 60101"。

> **注意：必须用上面这个 build 目录里的 `Server.exe`。**
> `bundled\Server\Server.exe` 是 2026-11-02 的旧构建，没有握手协议，
> 用它会看到「预检失败：服务端未响应握手」。

### 2. 确认端口

```bash
powershell -NoProfile -Command "Get-NetTCPConnection -LocalPort 60101 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess"
```

有输出说明在监听。程序实际用的是 60101

### 3. 跑压测

另开一个终端：

```bash
cd "D:/QtProjects/MyChat"
node test.js --clients 100 --ramp 40 --hold 20
```

脚本会自动往 `server.db` 里插入 `lt_1 .. lt_100` 测试账号（口令统一 `test123456`，
`pub_key` 留空所以不需要身份私钥），然后逐个连接、握手、登录、保持、心跳。

### 4. 收尾清账号

```bash
node test.js --clean
```

跑完一定要清，否则库里会留一堆 `lt_*` 账号。验证：

```bash
cd "D:/QtProjects/MyChat/Server/build/Q5_14_2_MinGW_32_bin_Release/release/Data/Database"
python -c "import sqlite3;print([r for r in sqlite3.connect('server.db').execute('select id,name from USERINFO')])"
```

应该只剩 `admin` / `bxz` / `123` 三个真实账号。

## 三、参数表

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--host <ip>` | `127.0.0.1` | 服务端地址，测远程机器时改这里 |
| `--port <n>` | `60101` | 服务端消息端口 |
| `--clients <n>` | `100` | 并发连接数 |
| `--ramp <n>` | `50` | 每秒建立多少个连接（爬坡速率）；**`0` 表示瞬时并发** |
| `--burst` | — | 等价于 `--ramp 0`，测一波涌入 |
| `--prefix <s>` | `lt_` | 测试账号前缀，多进程分片时错开账号段 |
| `--hold <s>` | `20` | 登录成功后保持多少秒 |
| `--hb <s>` | `5` | 心跳间隔秒数 |
| `--db <path>` | 自动查找 | 指定 `server.db` 路径 |
| `--seed <n>` | `0` | 只造 n 个账号后退出，不压测 |
| `--clean` | — | 删除所有 `lt_*` 测试账号后退出 |
| `--no-login` | — | 只测 TCP + 握手，跳过登录 |

完整帮助：

```bash
node test.js --help
```

## 四、常用场景命令

### 冒烟测试（确认链路通不通）

```bash
node test.js --clients 3 --ramp 10 --hold 6
```

3 个连接全部成功就说明协议、账号、端口都没问题。**调参数前先跑这个。**

### 标准压测（100 并发）

```bash
node test.js --clients 100 --ramp 40 --hold 30
```

### 找容量上限（逐级加压）

从 100 开始，每次加 100，直到成功率跌破 99% 或出现掉线：

```bash
node test.js --clients 200 --ramp 20 --hold 30
node test.js --clients 300 --ramp 20 --hold 30
node test.js --clients 500 --ramp 20 --hold 30
```

**关键：`--ramp` 保持在 20 左右。** 这里是想测"能稳住多少人"，就得让人一个一个上来；
几百个同时上来会把测试变成"上线冲击"（见六点二），两种数混在一起没有意义。

### 瞬时并发（一波人同时上线）

```bash
node test.js --clients 500  --burst --hold 30
node test.js --clients 1000 --burst --hold 30
```

`--burst` = `--ramp 0`，所有连接在同一轮事件循环里发起，不再排队。
输出会多两行：**建连延迟**（TCP 三次握手）和**建连窗口**（多少秒内全部 accept 完），
这两项跟握手延迟分开看，才能分清是网络层慢还是加密握手慢。

### 高并发（>150 自动调线程池，不用管环境变量）

```bash
node test.js --clients 500 --ramp 20 --hold 30
```

登录的 PBKDF2 走 libuv 线程池，默认只有 4 个线程。**并发超过 150 时脚本会自动带上
`UV_THREADPOOL_SIZE=32` 把自己重启一次**，第一条输出会提示：

```
线程池    并发 500 > 150，自动以 UV_THREADPOOL_SIZE=32 重启自身
```

所以 cmd、PowerShell、Git Bash 里都是同一条命令，不需要记各家的设变量语法。

想手动指定线程数也支持（比如调到 64），三种 shell 写法不同：

```bat
:: cmd
set "UV_THREADPOOL_SIZE=64" && node test.js --clients 500
```

```powershell
# PowerShell
$env:UV_THREADPOOL_SIZE=64; node test.js --clients 500
```

```bash
# Git Bash
UV_THREADPOOL_SIZE=64 node test.js --clients 500
```

> cmd 里 `UV_THREADPOOL_SIZE=32 node test.js` 会报「不是内部或外部命令」——
> 那是 bash 的语法，cmd 不认。现在脚本自动处理，写不写都行。

### 只测连接与握手容量（排除数据库干扰）

```bash
node test.js --clients 300 --ramp 20 --hold 10 --no-login
```

用来判断瓶颈在握手阶段还是登录阶段。两个数字对比：

- `--no-login` 也慢 → 瓶颈在握手（RSA 签名、密钥推导）
- 只有带登录才慢 → 瓶颈在数据库或 PBKDF2 线程池

### 测远程服务端

```bash
node test.js --host 192.168.1.50 --port 60101 --clients 100 --ramp 20
```

远程时脚本找不到 `server.db`，会跳过造号、假定账号已存在。这种场景要提前手工造号，
或者把 `--db` 指向一个本地副本：

```bash
node test.js --seed 200 --db "D:/tmp/server.db"
```

### 只造号 / 只清号（不压测）

```bash
node test.js --seed 500     # 造 lt_1..lt_500
node test.js --clean        # 全删
```

造号写的是 SQLite，**建议先停服务端再造号**，避免写锁争用。
服务端运行时脚本已设 `busy_timeout=8000`，一般也能成功，但并发写入时可能报 `database is locked`。

```

登录      启用（挑战-应答）
账号      .../server.db
          已就绪 100 个（lt_1 .. lt_100）

[0/3] 预检：确认服务端讲的是同一套协议 ...
      握手正常，服务端支持本协议

[1/3] 建立连接并完成握手/登录 ...
      连接+握手成功  100/100
      总耗时        2.5 s
      握手延迟      p50 67ms  p95 120ms  max 210ms
      登录成功      100/100
      登录延迟      p50 76ms  p95 140ms  max 240ms

[2/3] 保持 30s，每 5s 一次心跳 ...
      起始在线      100
      结束在线      100
      掉线          0
      心跳 RTT      p50 6.6ms  p95 12ms  max 20ms  (600 次)

[3/3] 结论
      有效在线      100 / 100  (100.0%)
      稳态在线      100  持续 30s
      本次 100 并发全部稳定，可继续加大 --clients 找上限。
      在线曲线  0s:100  3s:100  6s:100 ...
```

关注这四个指标：

| 指标 | 好的表现 | 变差说明什么 |
|---|---|---|
| **连接+握手成功** | 等于 `--clients` | 出现 `ECONNREFUSED` → accept 队列满，降 `--ramp` |
| **握手延迟 p95** | < 200 ms | 随并发线性上升 → 主线程串行开销（密钥解析、日志） |
| **掉线** | 0 | 心跳超时或被踢 → 判活逻辑或连接数上限 |
| **心跳 RTT p95** | < 50 ms | 升高说明事件循环被阻塞 |

## 六、本机实测基线（localhost，Qt5 Release）

### 优化前（GUI 线程被日志和用户表重建拖死）

| 并发 | 爬坡 | 结果 | 握手 p50 | 登录 p50 | 心跳 RTT p50 |
|---|---|---|---|---|---|
| 3 | 10/s | 3/3 | 10 ms | 10 ms | 0.7 ms |
| 100 | 40/s | 100/100 | 67 ms | 76 ms | 6.6 ms |
| 300 | 60/s | **271/300**（29 个 ECONNREFUSED） | 5106 ms | 10377 ms | 17.1 ms |
| 300 | 20/s | **300/300** | 8726 ms | 12862 ms | 53.6 ms |
| 500 | 20/s | **12/500**（122 个 ECONNREFUSED、319 个无 SH 回应） | 4892 ms | — | — |

瓶颈不在网络层，而在 GUI 线程，三处叠加：

1. 每条日志 `textBrowser->append()`，文档无上限增长，越写越慢
2. 每条日志还调一次 `QSystemTrayIcon::setToolTip()`，一次 Win32 `Shell_NotifyIcon`
3. **每次连接数变化都重建整张用户表** —— `getAllUser()` 查全表 + 逐条读头像文件 + 缩放成图标。
   爬坡时每秒 20 次，几百个账号就是每秒上万次磁盘读，这一条最致命

### 优化后（日志批量、托盘限频、用户表去抖）

| 并发 | 爬坡 | 结果 | 握手 p50 | 登录 p50 | 心跳 RTT p50 | 服务端 CPU |
|---|---|---|---|---|---|---|
| 500 | 20/s | **500/500** | 8 ms | 8 ms | 32.9 ms | — |
| 1000 | 20/s | **1000/1000** | 8 ms | 8 ms | 66.3 ms | — |
| 2000 | 30/s | **2000/2000** | 8 ms | 8 ms | 111 ms | 34 %（单核） |
| 3000 | 30/s | **3000/3000** | 9 ms | 8 ms | 172 ms | — |

全程零掉线、零 `ECONNREFUSED`。内存 158 MB（2000 连接时），服务端 7 个线程。

两点说明：

- **握手 p50 从 4892 ms 降到 8 ms**，这是同一台机器、同一份压测脚本的对比，
  唯一变量就是服务端那三处节流。
- **心跳 RTT 随并发线性上升**（1000 时 66 ms，3000 时 172 ms），
  这一项现在**大概率是压测端的问题**：单个 Node 进程扛 3000 条 socket、
  每秒 600 个心跳，事件循环自己就忙不过来。要测更高并发，得把 `--clients` 拆到
  多个进程/多台机器上跑，否则测到的是客户端的极限。

## 六点二、"并发"有两种，先分清测的是哪一种

| 口径 | 怎么打 | 回答的问题 | 瓶颈在哪 |
|---|---|---|---|
| **稳态在线容量** | `--ramp 20`，每秒放 20 个，慢慢爬 | 服务器能同时挂多少人、挂多久不掉 | 事件循环、内存、心跳扫描 |
| **瞬时并发冲击** | `--burst`，N 个 SYN 同一刻发出 | 一波人同时上线，能接住多少、多久全部就绪 | accept 速率、握手吞吐 |

第五章那张表（3000 并发零掉线）测的是**前者**：3000 人已经在线，靠心跳维持。
它并**不能**说明"3000 人同一秒上线"也扛得住 —— 上线那一下要跑完整的
RSA 验签 + X25519 + HKDF + 会话密钥封装，这一段在服务端是单线程串行的，
实测**每个连接约 5.3 ms**。

### 瞬时并发实测（localhost，`--no-login`，纯 TCP + 握手）

| 瞬时并发 | 建成连接 | 建连 p50 | 全部建成耗时 | 握手完成 p50 | 之后 8 s 掉线 |
|---|---|---|---|---|---|
| 200 | 200/200 | 74 ms | 0.09 s | 1.15 s | 0 |
| 500 | 500/500 | 154 ms | 0.19 s | 2.64 s | 0 |
| 1000 | 1000/1000 | 304 ms | 0.38 s | 5.32 s | 0 |
| 2000 | **1794/2000** | 667 ms | 0.81 s | 10.57 s | 0 |

怎么读这张表：

- **TCP 层很能扛**：1000 个 SYN 同一刻打进来，0.38 秒全部建连成功，
  accept 速率约 **2600 个/秒**，没有一个 `ECONNREFUSED`。
- **真正慢的是握手**：握手完成时间 ≈ N × 5.3 ms。1000 个要 5.3 秒，
  2000 个要 10.6 秒 —— 第 1000 个用户点完登录要等 5 秒才算"连上"。
  不是网络慢，是一个线程在逐个做非对称运算。
- **2000 开始出现拒绝**（206 个 `ECONNREFUSED`），accept 队列溢出。
  `--clients` 超过 1800 时才是真到顶了。

同样 200 个人，换个打法差别一个数量级：

| 打法 | 建连 p50 | 握手 p50 |
|---|---|---|
| `--ramp 20`（每秒 20 个） | 1 ms | 10 ms |
| `--burst`（同一刻 200 个） | 74 ms | 1148 ms |

所以被问"并发多少"时，先反问是哪种并发。可以这样答：
**同时在线 3000 不掉线；同一秒集中上线，1000 人以内 5 秒内全部就绪，
1800 人以内能全部接住（只是最后几个要等 10 秒），再往上才会出现连接被拒。**

注：**服务端启动后的头十几秒不要跑 burst** —— 主线程还在初始化用户表，
accept 会停滞，同样的 200 个会掉到 137 个，等 15 秒再测就正常。

## 六点三、做成无 UI 会不会更快？——实测：几乎不会

专门编了一个无界面版本 `ServerHeadless/`（`QCoreApplication` + `TcpMsgServer`，
不创建 `MainWindow`），同一份 `Data`、同一台机器、同一份压测脚本对比：

| 指标 | 带界面 | 无界面 |
|---|---|---|
| 1000 瞬时并发握手 p50 | 5318 ms | 5413 ms |
| 2000 连接稳态内存 | 158 MB | 118 MB |
| 线程数 | 7 | 4 |
| 掉线 | 0 | 0 |

握手差 1.8%，落在噪声里。原因很直接：**瓶颈是 OpenSSL 的非对称运算
（每连接约 5.3 ms），跟窗口有没有画出来没关系**。界面那点开销，在前面三处
节流（日志批量、托盘限频、用户表去抖）之后已经很低了。

无 UI 真正的收益不在速度：

- 内存少 40 MB（少一整套 Widgets + 托盘图标）
- 线程少 3 个
- 可以注册成 Windows 服务 / 开机自启，不怕有人把窗口关了、误点退出
- 能跑在没有桌面的机器（Server Core）上

所以：**想更快，改界面没用，要动握手（缓存 `EVP_PKEY`、握手放线程池）
或动线程模型（多核分摊）；想更省、更稳、更好部署，无 UI 才有意义。**

自己复现（`ServerHeadless/` 是独立工程，不影响 `Server/` 的构建，两个程序别同时开）：

```bash
cd ServerHeadless/build
qmake ../ServerHeadless.pro && mingw32-make -j4
# 运行时工作目录要指到有 Data/ 的地方
```

注意 `netdb/` 和 `comapi/` 在两个项目里各有一份副本，改协议时两边都要改。
细节见 `ServerHeadless/README.md`。

对照时的一个坑：第一版 headless 用了 `CONFIG += console`，`qDebug` 每条都要格式化
并写 stdout，1000 并发握手反而涨到 **12.4 秒**。改成和正式版一样的 windows 子系统
（无控制台）才可比 —— 否则测的是控制台输出，不是 UI。

## 六点五、往上加并发的路（按性价比排序）

| 优先级 | 做法 | 预期收益 | 代价 |
|---|---|---|---|
| 1 | 压测端多进程分片（`--clients` 拆成 4×750） | 先要知道真实上限，否则优化的可能是客户端 | 低 |
| 2 | 心跳间隔从 5 s 改到 15~30 s | 心跳流量降 3~6 倍，CPU 直接省下来 | 极低（改一行） |
| 3 | 服务端启动时缓存 `EVP_PKEY`，别每次握手都重新解析 PEM | 握手 5.3 ms/个 → 预计 2~3 ms | 低 |
| 4 | 登录写库改批量/异步（现在每次登录一次 fsync） | 爬坡阶段吞吐明显提升 | 中 |
| 5 | 握手放线程池并行做，主线程只收加密结果 | 1000 人同时上线的就绪时间从 5 s 压到 1 s 内 | 中（加密上下文按连接隔离） |
| 6 | 每个连接 `moveToThread` 或用多进程分摊 | 吃满多核，才能上 1 万 | 高（要处理共享状态加锁） |

实际做的时候，前 5 条都改完再谈第 6 条。现在的架构是**单线程事件循环**，
所有连接的处理天然串行，多核只用到一个；要真正用满机器，绕不开线程模型改造。

## 七、常见问题

**`预检失败：服务端未响应握手：TCP 已连接，但没有 SH 回应`**

**这是最常见的一个坑：跑错了 `Server.exe`。** 项目里有两份可执行文件：

| 路径 | 构建时间 | 支持握手 |
|---|---|---|
| `bundled\Server\Server.exe` | 2026-11-02 | **否**（没有握手协议，收到 CH 帧直接忽略） |
| `Server\build\...\release\Server.exe` | 2026-11-03 起 | 是 |

双击 `bundled` 里那个启动，端口照样监听 60101、TCP 也连得上，但它不认识 `{hs:"CH"}`，
于是一个字节都不回。旧版脚本里表现为 100 个连接各等 15 秒、最后一句「等待响应超时」；
现在会在预检阶段（2 秒内）直接报出来。

改用正确的新版：

```bash
cd "D:/QtProjects/MyChat/Server/build/Q5_14_2_MinGW_32_bin_Release/release"
./Server.exe
```

顺带一提：`bundled\Server\Data` 下还有**另一个** `server.db`。两个库不是同一个文件，
所以就算握手通了，用 bundled 服务端跑也会报口令错误——`lt_*` 账号造在 build 那个库里。
遇到这种情况用 `--db` 指到服务端真正使用的库。

**`ECONNREFUSED 127.0.0.1:60101`**
两种可能：① 服务端没起；② 起太猛了。先跑 `--clients 3 --ramp 10` 确认服务端活着，
再把 `--ramp` 降到 20 重试。

**`登录失败: 同一账号已在别处登录`（LoginRepeat）**
服务端不允许同一账号重复登录。脚本已给每个连接分配不同账号（`lt_1..lt_N`），
出现这个通常是上次压测的账号还挂在服务端在线表里——重启服务端，或先 `--clean` 再跑。

**`找不到 server.db，请用 --db 指定路径`**
脚本按 `Server/build/*/release/Data/Database/server.db` 自动找。构建目录名不同时会找不到，
用 `--db` 显式指定：

```bash
node test.js --seed 100 --db "D:/QtProjects/MyChat/Server/build/Q5_14_2_MinGW_32_bin_Release/release/Data/Database/server.db"
```

**大量 `等待响应超时`**
握手 15 秒没回。多见于服务端主线程被占满（同时有别的重任务），或者 `--ramp` 过大。

**`Cannot find module 'node:sqlite'`**
